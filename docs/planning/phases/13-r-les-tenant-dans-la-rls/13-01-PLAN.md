<decision id="Q1-security-definer">
**`current_tenant_role()` : PAS de SECURITY DEFINER.** Décision du planner, vérifiée sur la base locale le
2026-09-29 (`pg_get_functiondef('public.current_tenant_id'::regproc)`) :

```sql
CREATE OR REPLACE FUNCTION public.current_tenant_id()
 RETURNS uuid
 LANGUAGE sql
 STABLE
 SET search_path TO 'public'
AS $function$
  select tenant_id
  from public.profiles
  where id = auth.uid()
$function$
```

Le libellé du ROADMAP (« STABLE, SECURITY DEFINER, search_path figé ») est inexact : la fonction modèle réelle
n'est pas DEFINER. On suit le code réel, pour ces raisons :
1. Inutile : la policy `profiles_select_own` (`USING (id = auth.uid())`) laisse chaque utilisateur lire sa
   propre ligne ; aucune élévation n'est nécessaire.
2. Nuisible : les policies s'évaluent aussi pour `anon` (grants de table existants) ; une fonction DEFINER
   exécutable par PUBLIC relance le WARN « anon can execute SECURITY DEFINER function » du linter Supabase,
   que les Phases 10/12 ont justement fermé (`20260925090000_revoke_execute_from_public.sql`).
3. L'argument « search_path détourné » ne s'applique pas : le search_path est figé de toute façon.
4. Pas de récursion : aucune policy de `profiles` n'appelle `current_tenant_role()`.
5. EXECUTE reste accordé à PUBLIC par défaut (comme `current_tenant_id()`) — indispensable, les policies
   s'évaluent sous le rôle appelant, y compris `anon` ; pour `anon`, `auth.uid()` est NULL → la fonction
   renvoie NULL → aucun prédicat de rôle n'est vrai.
Le plan 03 corrige le libellé du requirement R1 dans le ROADMAP.
</decision>
